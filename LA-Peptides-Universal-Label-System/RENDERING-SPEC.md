# Rendering Specification

This document describes exactly how a finished label is generated by combining `master-label.svg`, `label-spec.json`, `layout.json`, `manifest.json`, a **brand-profile.json**, and a **product-profile.json**. It describes the actual, implemented algorithm — every step below is real code in `scripts/`, not aspirational. The reference implementation is `scripts/build-profile.js` (+ `scripts/build.js`'s `buildLabel()` core it calls into); read this document alongside those two files if you're porting the algorithm to another language/runtime.

## The five inputs, and what each is for

| File | Role |
|---|---|
| `master-label.svg` | The only visual/structural source. Every element has a stable id and a neutral placeholder value. Never regenerated, never brand-specific. |
| `label-spec.json` | The registry: which element ids exist, which are field-mappable (`fields`), how theme tokens map to element attributes (`themeTargets`, `fontTargets`), physical size/output targets. |
| `layout.json` | Percentage-based geometry for every region (for renderer-agnostic positioning), plus per-region `locked`, `defaultPlaceholder`, `alignment`, and `autoFit` metadata. |
| `manifest.json` | Package table of contents — not read by the build pipeline itself, but the discovery entry point for a human or system exploring the package for the first time. |
| `brand-profile.json` | One brand partner's identity + styling (see `schema/brand-profile.schema.json`). Sets once per partner, reused across all their products. |
| `product-profile.json` | One product/batch's content (see `schema/product-profile.schema.json`). A new batch = a new product-profile.json. |

## Algorithm

```
render(brandProfile, productProfile):
  1. VALIDATE
     errors, warnings = validateProfiles(brandProfile, productProfile, labelSpec)
     if errors: abort                      # required fields, malformed colors/URLs/dates, bad logo formats
     if warnings and strictMode: abort      # optional — see VALIDATION-RULES.md

  2. COMPOSE
     theme    = composeTheme(brandProfile)                     # -> {colors, fonts, logo, border, qrCaptionStyle}
     fieldMap = composeFieldMap(brandProfile, productProfile)   # -> {brand_name: ..., product_name: ..., ...}
     # see scripts/lib/composeProfiles.js for the exact field-by-field mapping

  3. LOAD
     doc = parse(master-label.svg)

  4. APPLY THEME
     for each entry in label-spec.json -> themeTargets:
       value = resolve(theme, entry.token)     # dotted-path lookup, e.g. "colors.primary"
       if value is not null: doc[entry.elementId].setAttribute(entry.attr, value)
     apply heading/subheading font-family overrides (label-spec.json -> fontTargets)
     rewrite the <style> block's body/mono font-family defaults

  5. APPLY FIELDS  (only fields present in fieldMap; absent optional fields keep the master's placeholder)
     for each entry in label-spec.json -> fields:
       value = fieldMap[entry.fieldKey]
       if value is null and entry.required: abort
       if value is null: continue  (placeholder stands)
       switch entry.applyAs:
         "text":      doc[entry.elementId].textContent = value
         "attr:href": copy the referenced local asset into the output dir (or pass through a "#symbol-id" /
                      remote URL unchanged), then set href + xlink:href to it
         "qr":        generate a real PNG QR code encoding `value` (coa_qr's value is always
                      product-profile.coaQrDestination), write it into the output dir, set href to it

  6. AUTO-FIT
     for each region in layout.json -> regions where region.autoFit.enabled:
       text = fieldMap[region.id]
       if text is null: continue                     # placeholder was already tuned to fit
       maxWidthPt = (region.width / 100) * layout.canvas.widthPt
       fontSize = shrink-to-fit(text, region.autoFit.baseFontSizePt, region.autoFit.minFontSizePt, maxWidthPt)
       if fontSize != baseFontSizePt: doc[region.id].setAttribute("font-size", fontSize)

  7. SERIALIZE (portable copy)
     write doc to <out>/label.svg                    # relative asset paths, human-editable

  8. RENDER (raster/vector copy — see "Why two copies" below)
     renderDoc = inline every <image> href as a base64 data URI (rasterizing any .svg source to PNG first)
     <out>/label-preview.png  = rasterize renderDoc at label-spec.json -> outputs.png.targetDpi
     <out>/label-print.pdf     = vector-render renderDoc at label-spec.json -> outputs.pdf size (exact pt)

  9. VERIFY
     re-open label-print.pdf, assert its page size matches outputs.pdf.width/height (±0.5pt)
     if mismatch: abort

  10. MANIFEST
     write <out>/manifest.json: template version, theme id, every applied field value,
     autofit decisions, PDF size verification result — full build provenance
```

## Why two copies of the SVG (portable vs. render)

`label.svg` (step 7) keeps ordinary relative file paths (`assets/logos/client-logo.svg`) so it stays a normal, human-editable file usable in Illustrator/Figma/Inkscape/Canva. The render copy (step 8) inlines every raster reference as a `data:image/png;base64,...` URI instead. This isn't a style choice — it works around a real limitation: modern librsvg (used for PNG rasterization) silently refuses to resolve local-file `<image>` hrefs, whether given as an absolute path, a relative path, a file input, or a buffer input. It fails with no error; the image is simply missing from the output. Data URIs are the only reliable fix, and they're also what the PDF vector renderer (pdfkit/svg-to-pdfkit) expects for embedded raster images anyway.

## brand-profile.json → theme mapping (composeTheme)

| brand-profile.json | Internal theme |
|---|---|
| `colors.background/primary/secondary/accent/border` | `theme.colors.*` (same names) |
| `colors.iconColor` (optional) | `theme.colors.darkAccent`, defaults to `colors.accent` if omitted |
| `fonts.heading/subheading/body/mono` | `theme.fonts.*` (same names); `subheading`/`mono` default to `body` if omitted |
| `logo.primary` | `theme.logo.primary` (fallback only — the field-map's `brand_logo` normally wins) |
| `border.thickness/radius` | `theme.border.*` |
| `qrStyle.caption` | `theme.qrCaptionStyle.text` |

## brand-profile.json + product-profile.json → field-map mapping (composeFieldMap)

Every `label-spec.json` fieldKey is identical to its brand-profile/product-profile source concept — see `schema/brand-profile.schema.json` and `schema/product-profile.schema.json`, each property's `description` states its `-> fieldKey` target directly. `product-profile.qrCaption`, if set, overrides `brand-profile.qrStyle.caption` for that one product. `product-profile.coaUrl`, if omitted, defaults to `coaQrDestination` with the URL scheme stripped.

## Reference implementation

```bash
node scripts/build-profile.js --brand brand-profiles/your-partner.brand-profile.json \
                                --product product-profiles/your-product.product-profile.json \
                                --out .build/your-product --zip
```

This is a complete, working renderer satisfying the brief above — not a stub. It's ~120 lines across `scripts/build-profile.js` and `scripts/build.js`'s `buildLabel()`, delegating to the small, single-purpose modules in `scripts/lib/`. Port it to another language by re-implementing steps 1–10 against the same three JSON files; nothing about the algorithm is Node-specific.
